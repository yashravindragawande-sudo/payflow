# PayFlow

A simplified REST API for a UPI-style wallet system: register users, look them up,
and record money transfers between them. Built with Spring Boot, Spring Data JPA,
and an in-memory H2 database.

---

## 1. How to Run

**Prerequisites:** Java 17+, Maven (or use the included `mvnw` wrapper if you generate
one via Spring Initializr).

```bash
# from the project root
mvn spring-boot:run
```

## 2. Project Structure

```
src/main/java/com/payflow/
├── PayflowApplication.java     # entry point
├── entity/                     # @Entity classes - the data model
│   ├── User.java
│   └── Transaction.java
├── repository/                 # Spring Data JPA interfaces - the data access layer
│   ├── UserRepository.java
│   └── TransactionRepository.java
├── service/                    # @Service classes - business logic layer
│   ├── UserService.java
│   └── TransactionService.java
└── controller/                 # @RestController classes - HTTP layer
    ├── UserController.java
    └── TransactionController.java
```

**What each layer does:**
- **entity** — plain Java classes annotated with `@Entity` that map directly to
  database tables. This is the data model; each field becomes a column.
- **repository** — interfaces extending `JpaRepository`. Spring Data JPA generates
  the implementation at runtime, giving CRUD operations and custom lookups
  (`findByUpiId`, `@Query` methods) with no SQL or implementation code written
  by hand.
- **service** — holds business logic and orchestrates repository calls. Right now
  it's a thin pass-through, but this is where rules like "balance can't go
  negative" would eventually live.
- **controller** — exposes the service layer over HTTP. Handles routing, request
  parsing (`@RequestBody`, `@PathVariable`), and building `ResponseEntity`
  responses.

## 3. Spring Boot's Three Features, in PayFlow specifically

1. **Embedded server** — There is no separate Tomcat installation anywhere in this
   project. Running `mvn spring-boot:run` starts an embedded Tomcat instance
   directly inside the JVM process on port 8080 (configured in
   `application.properties`). Nothing needed to be installed or deployed to a
   servlet container.

2. **Auto-configuration** — Simply having `spring-boot-starter-data-jpa` and `h2`
   as Maven dependencies caused Spring Boot to automatically configure a
   `DataSource` pointing at the in-memory H2 database, a `LocalContainerEntityManagerFactoryBean`,
   and a `PlatformTransactionManager` — none of which was configured by hand.
   Similarly, having `spring-boot-starter-web` on the classpath auto-configured
   Jackson as the JSON (de)serializer used by `@RequestBody`/`@RestController`.

3. **Production-ready defaults** — Sensible defaults are applied without any setup:
   Jackson is wired up to serialize `LocalDateTime` sensibly, Hibernate's
   `ddl-auto=update` auto-generates schema from entities, and the embedded
   Tomcat comes with reasonable default thread pool and connection settings out
   of the box. (Spring Boot Actuator, which adds health/metrics endpoints, was
   not added here but is the more advanced example of this feature.)

## 5. Task 3 — `findByUpiId` Generated SQL

Calling `userRepository.findByUpiId("priya@okaxis")` produces JPQL:

```
select u from User u where u.upiId = ?1
```

which Hibernate translates into SQL like:

```sql
select
    u1_0.id,
    u1_0.balance,
    u1_0.name,
    u1_0.phone_number,
    u1_0.upi_id
from
    user u1_0
where
    u1_0.upi_id=?
```

**(a) How JPA derives it from the method name:** Spring Data JPA parses the method
name token by token. `findBy` signals "build a SELECT query." Everything after
`findBy` — `UpiId` — is matched against the entity's property names. Since `User`
has a property `upiId`, Spring Data JPA builds a `WHERE upi_id = ?` clause. No
query is written by hand; the method signature *is* the query specification.

**(b) What the `?` placeholder means:** It's a positional bind parameter (JDBC
`PreparedStatement` parameter). The actual `upiId` argument passed into the
method is sent to the database separately from the SQL text and substituted in
safely at execution time — this is what prevents SQL injection, unlike string
concatenation.

### `@RequestBody` demonstration

```bash
# WITH @RequestBody -> fields populate correctly
curl -X POST http://localhost:8080/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Test User","upiId":"test@okicici","phoneNumber":"9999999999","balance":100.0}'

# WITHOUT @RequestBody (hits the /no-body-demo endpoint, which omits the annotation)
curl -X POST "http://localhost:8080/users/no-body-demo" \
  -H "Content-Type: application/json" \
  -d '{"name":"Test User","upiId":"test@okicici","phoneNumber":"9999999999","balance":100.0}'
# -> returns "name=null, upiId=null, phoneNumber=null, balance=null"
```

**Why the fields are null without `@RequestBody`:** Without the annotation, Spring
MVC does not treat the incoming payload as JSON to deserialize into the method
parameter. Instead, it falls back to its default data-binding behavior, which
tries to populate the object's fields from request *parameters* (query string
or form-encoded fields) using setter methods matched by name. A raw JSON body
sent with `Content-Type: application/json` is never parsed for this binding —
Spring has no message converter step running — so every property on the bound
`User` object is left at its default value (`null` for objects). `@RequestBody`
is what explicitly tells Spring "read the HTTP body, run it through the
Jackson `HttpMessageConverter`, and deserialize it into this parameter" — that
extra converter step is exactly what's missing otherwise.

## 7. Task 6 — Comparing the Three Custom Query Approaches

1. **Derived query methods** (e.g. `findByUpiId(String upiId)`) — Spring Data JPA
   parses the method name into a query automatically. Fast to write for simple
   lookups, fully type-safe, but method names get unwieldy for complex
   conditions (e.g. `findByBalanceGreaterThanAndNameContainingOrderByBalanceDesc`).

2. **`@Query` with JPQL** (e.g. `findUsersWithBalanceAbove`) — You write the query
   yourself using entity/property names (`User`, `u.balance`) instead of table/
   column names. Still database-agnostic (JPQL is translated to whichever SQL
   dialect Hibernate is configured for), and far more readable than a long
   derived method name for complex conditions.

3. **Native SQL** (`@Query(nativeQuery = true)`) — You write actual SQL against
   the real table/column names.

**Why native queries are least preferred:** Native SQL ties the code directly
to one database's SQL dialect and physical schema (table/column names), so
switching databases (e.g. H2 in dev to Postgres in prod) or renaming a column
can silently break queries that JPQL/derived methods would have adapted to
automatically. It also bypasses some JPA-level optimizations and loses the
extra compile-time/property-name validation that JPQL and derived methods get
by referencing entity properties instead of raw strings.

## 8. Conceptual Write-Up

**Request lifecycle:** When `curl` sends `POST /users`, the request first hits the
embedded Tomcat server, which hands it to Spring's front controller, the
**DispatcherServlet**. The DispatcherServlet consults the `HandlerMapping` to
find which controller method matches `POST /users` (here, `UserController.registerUser`),
then delegates execution to the matching **HandlerAdapter**, which knows how to
invoke that specific method signature — including running the `@RequestBody`
JSON deserialization before calling it. Once `createUser`/`registerUser` runs
and returns a `ResponseEntity`, the HandlerAdapter hands the return value back
to the DispatcherServlet, which uses an `HttpMessageConverter` (Jackson) to
serialize it back into a JSON HTTP response.

**Serialisation:** Jackson, auto-configured because `spring-boot-starter-web` is
on the classpath, converts the incoming JSON body into a `User` object. It does
this by matching JSON keys to the object's fields/setters by name. If the key
is `"upi_id"` instead of `"upiId"`, Jackson will not match it to the `upiId`
field by default (Jackson expects exact camelCase field names unless a naming
strategy or `@JsonProperty` annotation is configured), so `upiId` on the
resulting `User` object will simply be `null` instead of throwing an error.

**Spring Boot features:** The three features are (1) an embedded server, (2)
auto-configuration, and (3) production-ready defaults. In PayFlow: (1) the app
runs via `mvn spring-boot:run` with Tomcat embedded in the JVM, no external
server install; (2) adding the JPA/H2 starter dependencies alone caused
`DataSource`, `EntityManagerFactory`, and transaction management beans to be
configured automatically; (3) `ddl-auto=update` and Hibernate's sensible SQL
dialect defaults mean the two tables get created correctly with zero manual
schema-definition SQL.

**Spring vs. Spring Boot:** With plain Spring, this project would have required
manually configuring a `DataSource` bean, an `EntityManagerFactory` bean, a
`TransactionManager` bean, a `DispatcherServlet` registered in `web.xml` (or a
`WebApplicationInitializer`), and a JSON message converter bean for Jackson —
all typically via explicit `@Configuration` classes or XML. Spring Boot takes
care of every one of these automatically the moment the relevant starter
dependency is on the classpath, based on auto-configuration and sensible
defaults, cutting the setup from dozens of lines of config to a single
`@SpringBootApplication` class.

**Stateless REST:** Stateless means the server keeps no memory of a client's
previous requests between calls — every request must carry all the information
needed to process it (here, the full sender/receiver/amount payload), and the
server doesn't rely on any session data left over from an earlier request. This
matters once PayFlow runs on three servers behind a load balancer because the
load balancer can send any given request to any of the three servers with no
guarantee it's the same one that handled the client's previous request. If the
server depended on in-memory state from a prior request, a request routed to a
different instance would fail or behave inconsistently; statelessness is what
makes horizontal scaling behind a load balancer work correctly.

**Persistence:** If transactions were stored in a Java `List` instead of the H2
database, that list would live only in the JVM's heap memory for as long as the
process is running. Restarting the server would wipe the list clean — every
transaction ever recorded would be gone, with no way to recover it. This is
completely unacceptable for a payments application because transaction records
are the authoritative, legally/financially significant history of money
movement; losing them on every restart (or crash) would make balances
unverifiable and the whole system untrustworthy. Persisting to a real database
means data survives restarts, crashes, and deployments.
